# 마스터 관리(기준정보) 시스템 PRD

> 이 문서는 `docs/prd/PRD_MVP.md`(사내 ERP 시스템 MVP PRD)의 후속 문서로, **마스터 관리 > 기준정보 관리** 영역을 상세 설계한다. 기존 메뉴 트리에 "메뉴 데이터만 등록된 뼈대"로 존재하던 기준정보 관리 6개 화면을 재구성하고, 실제 CRUD 로직·데이터 모델·권한을 정의한다. **상품(Product) 관리는 메뉴 재구성 대상에서는 제외**하지만, 마스터 데이터를 참조하는 소비자(consumer)이자 사용자가 명시적으로 요청한 화면이므로 속성 명세와 화면 설계를 함께 다룬다.

---

## 1. 개요 및 목표

### 1.1 배경

- 현재 `menus` 테이블에는 "마스터 관리 > 기준정보 관리" 하위에 법인/브랜드/소브랜드/아이템·서브아이템/상품 컬러/상품 사이즈 6개 소분류가 **메뉴 데이터만** 등록되어 있고 실제 화면 로직은 없다 (`PRD_MVP.md` F011, Phase 2 이후).
- 실제 운영에 필요한 마스터 엔티티는 법인부터 사이즈까지 총 11종이며, 상호 계층(부모-자식) 관계를 가진다. 기존 6개 화면 구성으로는 이 계층을 다 담지 못한다 (예: 라인·아이템타입·컬러타입 등이 누락).
- 메뉴 트리는 구조상 **대분류/중분류/소분류 3단계**까지만 지원하므로, 11종 엔티티를 모두 개별 소분류로 펼치면 좌측 트리가 지나치게 길어지고 상위 계층 선택을 화면 이동마다 반복해야 한다.

### 1.2 목표

- 계층적으로 연관된 마스터 엔티티를 **의미 단위(체인)로 묶어 5개 화면**으로 재구성하고, 각 화면 내부는 "좌측 트리 탐색 + 우측 리스트/폼(마스터-디테일)" 패턴으로 계층을 표현한다.
- 신규/기존 관리자가 코드 체계·계층 구조를 이해하기 쉽도록 화면명·메뉴명을 실제 업무 용어로 정리한다.
- 기준정보 관리 5개 화면은 **관리자(admin)·최고관리자(superadmin)만 접근 가능**하도록 역할 기반 접근 제어를 추가한다 (기존 `user_menu_permissions` 개별 권한 부여와는 별개로 역할 하드 게이트를 적용).
- 상품(Product) 관리는 이번 문서에서 속성·화면을 설계하되, 메뉴 위치와 접근 권한(오픈 상태 유지)은 변경하지 않는다.
- 각 마스터 엔티티(성별 제외)와 상품에 대해 더미 데이터 10건씩을 정의해 개발·QA 단계에서 즉시 사용할 수 있게 한다.

### 1.3 이번 문서가 아닌 것 (비범위 요약, 상세는 12장)

- 상품(Product)의 메뉴 트리 위치 변경, 상품 정보 현황/일괄 수정 화면 상세 설계
- 재고, 발주, 매입/매출 등 상품 이후 단계의 운영 기능
- 다국어(ko/en/ja/zh) 번역 적용 (기존 관례상 관리자 전용 내부 화면은 한국어만 지원, `PRD_MVP.md` 4.1과 동일 기조)

## 3. 사용자 및 권한 모델

기존 `PRD_MVP.md` 4장의 모델을 그대로 재사용한다. `profiles.role`은 `user` / `admin` / `superadmin` 세 값을 가지며, DB 함수 `is_admin()`(admin·superadmin 모두 true)과 `is_superadmin()`(superadmin만 true)이 이미 구현되어 있다.

### 3.1 화면별 접근 규칙

| 화면 그룹 | 접근 가능 역할 | 근거 |
| --- | --- | --- |
| 기준정보 관리 5개 화면 (법인~사이즈) | `admin`, `superadmin`만 | 사용자 요청: "상품관리를 제외한 나머지 관리 기능은 관리자, 최고관리자만" |
| 상품 관리 (상품 등록/수정, 현황, 일괄 수정) | 기존과 동일 — `user_menu_permissions`로 개별 부여된 사용자 + admin/superadmin | 변경 없음, 오픈 상태 유지 |
| 기본 관리 (사용자/메뉴/권한 관리) | `admin`, `superadmin`만 | 기존 `PRD_MVP.md` F005~F007과 동일, 변경 없음 |

- 기준정보 관리 화면은 `user_menu_permissions`에 개별 권한이 부여되어 있더라도 `role`이 `user`이면 접근할 수 없다. 즉 **"메뉴 노출 권한"과 "역할 기반 하드 게이트"를 함께 적용**하는 이중 체크가 필요하다 (Route Handler/Server Component 진입 시 `getClaims()` → `profiles.role` 재확인 → 아니면 `/erp/forbidden`).
- 서버 측 RLS는 각 마스터 테이블에 대해 `SELECT`는 로그인 사용자 전체 허용(상품 등록 폼의 드롭다운에서 라인/컬러/사이즈를 조회해야 하므로), `INSERT`/`UPDATE`/`DELETE`는 `is_admin()`(즉 admin 또는 superadmin)만 허용한다 (9장 상세).

## 4. 메뉴 구조 재설계

### 4.1 기존 구조 (DB `menus` 테이블 현재 상태)

```
📁 마스터 관리
├── 📂 기본 관리
│   ├── 사용자 관리
│   ├── 메뉴 관리
│   └── 사용자 권한 관리
├── 📂 기준정보 관리                 ← 재구성 대상
│   ├── 법인 관리
│   ├── 브랜드 관리
│   ├── 소브랜드 관리
│   ├── 아이템/서브아이템 관리
│   ├── 상품 컬러 관리
│   └── 상품 사이즈 관리
└── 📂 상품 관리                     ← 변경 없음 (화면 설계만 이번 문서에서 진행)
    ├── 상품 관리
    ├── 상품 정보 현황
    └── 상품 정보 일괄 수정
```

### 4.2 신규 구조 (안)

```
📁 마스터 관리
├── 📂 기본 관리                    변경 없음
│   ├── 사용자 관리
│   ├── 메뉴 관리
│   └── 사용자 권한 관리
├── 📂 기준정보 관리                 ★ 재구성 (6개 → 5개, 관리자/최고관리자 전용)
│   ├── 법인 관리                        법인 단독 (최상위, 계층 없음)
│   ├── 브랜드 구조 관리                 법인 > 브랜드 > (소브랜드 | 라인)
│   ├── 상품 분류 관리                   소브랜드 > 아이템타입 > 아이템 > 서브아이템
│   ├── 컬러 관리                        브랜드 > 컬러타입 > 컬러
│   └── 사이즈 관리                      브랜드 > 성별(상수) > 사이즈타입 > 사이즈
└── 📂 상품 관리                    변경 없음
    ├── 상품 관리                        ★ 이번 문서에서 화면 상세 설계
    ├── 상품 정보 현황                   변경 없음 (Out of scope)
    └── 상품 정보 일괄 수정              변경 없음 (Out of scope)
```

- 계층적으로 연결된 엔티티를 화면 단위로 묶은 이유: 메뉴 트리가 3단계(대/중/소)로 제한되어 있어 11종 엔티티를 모두 소분류로 펼치면 상위 선택(법인→브랜드)을 화면마다 반복해야 한다. 화면 내부에서 좌측 트리로 계층을 탐색하는 쪽이 클릭 수가 적고 맥락 유지가 쉽다. 이미 기존 구조의 "아이템/서브아이템 관리"가 2개 엔티티를 한 화면에 묶은 선례이기도 하다.
- "브랜드 구조 관리"에서 소브랜드와 라인은 모두 브랜드의 직계 자식이지만 서로 형제 관계(소브랜드 ≠ 라인의 상위)이므로, 좌측 트리에 가상 그룹 노드 "소브랜드"/"라인"을 두어 구분한다 (7.2절 와이어프레임 참고).

### 4.3 메뉴 데이터 마이그레이션 매핑 (구현 시 참고)

| 기존 메뉴 (id) | 처리 | 신규 메뉴명 |
| --- | --- | --- |
| 법인 관리 (`d511a97c-...`) | 이름 유지 | 법인 관리 |
| 브랜드 관리 (`c5d91f1a-...`) | 이름 변경 | 브랜드 구조 관리 |
| 소브랜드 관리 (`dbbde663-...`) | **삭제** (브랜드 구조 관리로 통합) | — |
| 아이템/서브아이템 관리 (`8bdbe430-...`) | 이름 변경 | 상품 분류 관리 |
| 상품 컬러 관리 (`48641dd2-...`) | 이름 변경 | 컬러 관리 |
| 상품 사이즈 관리 (`2db7f963-...`) | 이름 변경 | 사이즈 관리 |

`sort_order`는 법인(0) → 브랜드 구조(1) → 상품 분류(2) → 컬러(3) → 사이즈(4) 순으로 재정렬한다.

## 5. 마스터 데이터 전체 계층 구조

```
법인 (Company)
└── 브랜드 (Brand)
    ├── 소브랜드 (Small Brand)
    │   └── 아이템타입 (Item Type, 대분류)
    │       └── 아이템 (Item, 중분류)
    │           └── 서브아이템 (Sub Item, 소분류)
    │               └── 상품 (Product)  ← 라인/컬러/성별/사이즈를 추가로 참조
    ├── 라인 (Brand Line)  ─────────────┐
    ├── 컬러타입 (Brand Color Type)      │  상품이 참조하는
    │   └── 컬러 (Brand Color)           │  브랜드 하위 속성들
    └── 성별 (Gender, 상수 3종)          │  (서브아이템 체인과는
        └── 사이즈타입 (Brand Gender Size Type)  │  별도 축)
            └── 사이즈 (Brand Gender Size) ──────┘
```

- **분류 축(세로)**: 법인 → 브랜드 → 소브랜드 → 아이템타입 → 아이템 → 서브아이템 → 상품. 상품이 "어떤 카테고리에 속하는가"를 결정.
- **속성 축(가로)**: 브랜드 하위의 라인/컬러/사이즈는 분류 축과 독립적으로 상품에 부여되는 속성값. 상품은 분류 축의 리프(서브아이템)에 속하면서 동시에 같은 브랜드의 라인/컬러/사이즈를 선택한다.
- 상품 등록 시 라인·컬러타입·사이즈타입은 반드시 **서브아이템이 속한 브랜드와 동일한 브랜드**의 하위 데이터여야 한다 (교차 브랜드 선택 방지 — 폼 검증 규칙, 8.6절 참고).

## 6. 공통 설계 원칙

### 6.1 코드 자동 채번 규칙

모든 마스터 코드는 **등록 시 자동 채번되며, 등록 후 관리자가 직접 수정할 수 있다** (중복 시 서버에서 재검증 후 에러 반환).

| 엔티티 | 접두사 | 자릿수 | 예시 | 채번 범위 |
| --- | --- | --- | --- | --- |
| 법인 | `C` | 4 | `C1001` | 전체 |
| 브랜드 | `B` | 4 | `B1001` | 전체 |
| 소브랜드 | `SB` | 4 | `SB1001` | 전체 |
| 아이템타입(대분류) | `LC` | 4 | `LC1001` | 전체 |
| 아이템(중분류) | `MC` | 4 | `MC1001` | 전체 |
| 서브아이템(소분류) | `SC` | 4 | `SC1001` | 전체 |
| 라인 | `BL` | 4 | `BL1001` | 전체 |
| 컬러타입 | `BCT` | 4 | `BCT1001` | 전체 |
| 컬러 | `BC` | 7 | `BC1000001` | 전체 |
| 성별 (상수) | `GE` | 4 | `GE1001` | 고정 3건, 채번 없음 |
| 사이즈타입 | `BGST` | 4 | `BGST1001` | 전체 |
| 사이즈 | `BGS` | 4 | `BGS1001` | 전체 |
| 상품 | `PM` | 9 | `PM100000001` | 전체 |

> 채번 범위는 "전체 시퀀스(부모와 무관하게 증가)"로 통일한다. 부모별로 채번을 끊으면(예: 브랜드마다 SB0001부터 재시작) 코드만으로 소속을 알 수 없어 혼동을 유발하기 때문이다.

### 6.2 모든 마스터 엔티티 공통 속성

사용자가 요청한 "일반 속성"으로 아래 컬럼을 전 엔티티(성별 제외, 상품 포함)에 공통 적용한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `code` | text, unique | 6.1절 규칙으로 자동 채번, 수정 가능 |
| `name` | text | 명칭 |
| `sort_order` | integer, default 0 | 목록 표시 순서 (드래그 정렬 또는 숫자 입력) |
| `is_active` | boolean, default true | 사용여부. 비활성화 시 하위 화면 드롭다운에서 숨김(과거 데이터는 유지) |
| `note` | text, nullable | 비고 |
| `created_at` / `updated_at` | timestamptz | 기존 프로젝트 관례 |
| `created_by` / `updated_by` | uuid → `profiles.id` | 변경 이력 추적 |

### 6.3 화면 공통 UI 패턴 — 마스터-디테일

기준정보 관리 5개 화면은 모두 동일한 레이아웃 패턴을 따른다.

```
┌─────────────────────────────────────────────────────────┐
│ [화면 제목]                                    [+ 등록]   │
├───────────────────┬─────────────────────────────────────┤
│ 좌측: 상위 계층 트리 │ 우측: 선택된 노드의 하위 목록(테이블)    │
│  검색창             │  코드 / 명칭 / 사용여부 / 정렬순서 / 비고│
│  ▾ 법인1            │  [행 클릭 → 우측 슬라이드 패널에서       │
│    ▾ 브랜드1         │   상세 조회/수정, 사용여부 토글,        │
│      · 소브랜드1     │   삭제(참조 데이터 있으면 비활성화만    │
│      · 소브랜드2     │   허용)]                              │
│  ▸ 법인2            │                                       │
└───────────────────┴─────────────────────────────────────┘
```

- 좌측 트리는 선택 상태를 유지한 채 우측만 갱신되는 방식(트리 리렌더 없음)으로 탐색 흐름을 끊지 않는다.
- 상위 노드를 비활성화(`is_active=false`)하면 하위 신규 등록 시 드롭다운에서 제외되지만, 기존 하위 데이터는 그대로 조회 가능하다.
- 삭제는 하위 참조가 없는 경우에만 물리 삭제를 허용하고, 참조가 있으면 "사용여부 끄기"만 안내한다 (예: 이미 상품이 연결된 컬러는 삭제 불가).

## 7. 화면별 상세 설계

### 7.1 법인 관리

- **계층**: 최상위, 단독 엔티티.
- **화면 구성**: 좌측 트리 없이 단일 목록 + 등록/수정 슬라이드 패널 (5개 화면 중 유일하게 마스터-디테일이 아닌 단순 목록형).
- **필드**: 법인코드(자동, `C####`), 법인명, 사용여부, 정렬순서, 비고.
- **참조 관계**: 브랜드가 법인을 FK로 참조. 법인 삭제는 하위 브랜드가 없을 때만 허용.

### 7.2 브랜드 구조 관리 (브랜드 / 소브랜드 / 라인)

- **계층**: 법인 > 브랜드 > (소브랜드, 라인) — 소브랜드와 라인은 브랜드의 형제 자식.
- **화면 구성**:

```
┌───────────────────┬─────────────────────────────────────┐
│ ▾ 법인1             │ [소브랜드] [라인]  ← 탭              │
│   ▾ 브랜드1          │                                     │
│     ▸ 소브랜드 (3)   │  코드 / 명칭 / 사용여부 / 정렬 / 비고 │
│     ▸ 라인 (2)       │  SB1001 소브랜드1  ...               │
│   ▸ 브랜드2          │  SB1002 소브랜드2  ...               │
│ ▸ 법인2              │                                     │
└───────────────────┴─────────────────────────────────────┘
```

- 좌측 트리에서 "브랜드"를 선택하면 우측에 [소브랜드]/[라인] 탭이 나타나고, 탭별로 해당 브랜드 하위 목록을 관리한다.
- **필드(브랜드)**: 브랜드코드(`B####`), 브랜드명, 소속 법인(FK, 필수), 사용여부, 정렬순서, 비고.
- **필드(소브랜드)**: 소브랜드코드(`SB####`), 소브랜드명, 소속 브랜드(FK, 필수), 사용여부, 정렬순서, 비고.
- **필드(라인)**: 라인코드(`BL####`), 라인명, 소속 브랜드(FK, 필수), 사용여부, 정렬순서, 비고.

### 7.3 상품 분류 관리 (아이템타입 / 아이템 / 서브아이템)

- **계층**: 소브랜드 > 아이템타입(대분류) > 아이템(중분류) > 서브아이템(소분류) — 4단 순차 체인.
- **화면 구성**: 상단에 법인/브랜드/소브랜드 선택(브레드크럼 또는 3단 드롭다운)으로 시작점을 좁힌 뒤, 좌측 트리에 아이템타입→아이템→서브아이템을 그대로 표시. 우측에 선택 노드의 하위 목록.
- **필드**: 각 레벨 공통으로 코드(`LC####`/`MC####`/`SC####`), 명칭, 상위 FK, 사용여부, 정렬순서, 비고.

### 7.4 컬러 관리 (컬러타입 / 컬러)

- **계층**: 브랜드 > 컬러타입 > 컬러.
- **화면 구성**: 상단 브랜드 선택 드롭다운 → 좌측 컬러타입 목록 → 우측 컬러 카드/그리드(색상 스와치 표시).
- **필드(컬러타입)**: 컬러타입코드(`BCT####`), 컬러타입명, 소속 브랜드(FK), 사용여부, 정렬순서, 비고.
- **필드(컬러)**: 컬러코드(`BC#######`), 컬러명, 소속 컬러타입(FK), **RGB 색상값(6자리 HEX, 필수, 예: `FF5733`)**, 사용여부, 정렬순서, 비고. 등록/수정 폼에 컬러 피커(HEX 입력 + 미리보기 스와치)를 제공한다.

### 7.5 사이즈 관리 (성별 / 사이즈타입 / 사이즈)

- **계층**: 브랜드 > 성별(상수 3종) > 사이즈타입 > 사이즈.
- **성별은 CRUD 화면 없이 고정 상수**로 취급한다 (아래 표). 코드/화면 어디에도 등록·수정·삭제 UI를 두지 않는다.

  | 코드 | 이름 |
  | --- | --- |
  | `GE1001` | 남성 |
  | `GE1002` | 여성 |
  | `GE1003` | 혼용 |

- **화면 구성**: 상단 브랜드 선택 → 성별 탭(남성/여성/혼용, 3개 고정 탭) → 좌측 사이즈타입 목록 → 우측 사이즈 목록.
- **필드(사이즈타입)**: 사이즈타입코드(`BGST####`), 사이즈타입명, 소속 브랜드(FK), 성별(고정값 선택, 필수), 사용여부, 정렬순서, 비고.
- **필드(사이즈)**: 사이즈코드(`BGS####`), 사이즈명, 소속 사이즈타입(FK), 사용여부, 정렬순서, 비고.

### 7.6 상품(Product) 관리

메뉴 위치(마스터 관리 > 상품 관리 > 상품 관리)와 접근 권한(오픈, 기존 `user_menu_permissions` 방식 유지)은 변경하지 않는다. 화면 상세만 이번 문서에서 설계한다.

#### 7.6.1 목록 화면

```
┌─────────────────────────────────────────────────────────┐
│ [검색: 상품코드/상품명] [브랜드▾][서브아이템▾][성별▾][사용여부▾] [+ 상품등록]│
├───┬────────┬──────────┬──────┬──────┬────┬──────┬────────┤
│썸네일│상품코드 │ 상품명    │ 라인  │ 컬러  │성별│ 사이즈│ 사용여부│
├───┼────────┼──────────┼──────┼──────┼────┼──────┼────────┤
│ 🖼 │PM1000...│ 상품 1    │ 라인1 │ 컬러1 │남성│ S    │  ✅    │
└───┴────────┴──────────┴──────┴──────┴────┴──────┴────────┘
```

- 목록의 썸네일 컬럼은 **썸네일 이미지(상품관리용, 축소본)** 를 사용한다. 상세/등록 폼에서는 원본 **상품 이미지(쇼핑몰용)** 를 크게 보여준다.
- 썸네일은 상품 이미지 업로드 시 서버(또는 엣지 함수)에서 **자동 리사이즈 생성**하는 것을 기본안으로 제안한다(별도 파일을 관리자가 다시 업로드하지 않도록). 별도 업로드가 필요하면 후속 화면 설계 단계에서 토글 옵션으로 추가한다.

#### 7.6.2 등록/수정 폼

| 구분 | 필드 | 타입/제약 | 설명 |
| --- | --- | --- | --- |
| 핵심 | 상품코드 | 자동 채번(`PM#########`), 수정 가능 | 6.1절 규칙 |
| 핵심 | 상품명 | text, 필수 | — |
| 분류 | 서브아이템 | FK, 필수 | 법인→브랜드→소브랜드→아이템타입→아이템→서브아이템 단계별 드롭다운(캐스케이드)으로 최종 선택 |
| 속성 | 라인 | FK, 필수 | 서브아이템이 속한 브랜드 하위 라인만 노출 |
| 속성 | 컬러 | FK, 필수 | 서브아이템이 속한 브랜드 하위 컬러만 노출, 선택 시 색상 스와치 표시 |
| 속성 | 성별 | 상수 선택, 필수 | 남성/여성/혼용 |
| 속성 | 사이즈 | FK, 필수 | 선택된 브랜드+성별에 해당하는 사이즈타입의 사이즈만 노출 |
| 이미지 | 상품 이미지 | 업로드, 필수 | 쇼핑몰 노출용 원본. `file-dropzone` 컴포넌트 재사용 |
| 이미지 | 썸네일 이미지 | 자동 생성(또는 수동 업로드) | 상품 리스트 전용 축소본 |
| 일반(제안) | 시즌 | text/select | 예: 26SS, 25FW |
| 일반(제안) | 출시연도 | integer | — |
| 일반(제안) | 소재 | text | — |
| 일반(제안) | 원가 / 판매가 | numeric | — |
| 일반(제안) | 판매상태 | select (판매중/품절/단종) | `is_active`와 별개의 영업 상태값 |
| 공통 | 사용여부, 정렬순서, 비고 | 6.2절 공통 속성 | — |

> "일반 속성"은 사용자가 구체 항목을 지정하지 않아 ERP 의류 도메인 관례에 따라 제안한 값이다. 실제 구현 전 확정 필요(13장 리스크 참고).
> 폼 검증 규칙: 라인·컬러·사이즈의 소속 브랜드가 서브아이템의 소속 브랜드와 다르면 저장을 막고 에러 메시지를 표시한다(교차 브랜드 조합 방지).

## 9. 권한 / RLS 설계

- 신규 테이블 전체에 RLS를 활성화한다.
- **SELECT**: 로그인 사용자(`auth.uid() is not null`) 전체 허용 — 상품 관리 화면의 드롭다운이 기준정보 데이터를 읽어야 하기 때문.
- **INSERT / UPDATE / DELETE**: `public.is_admin()`(admin 또는 superadmin)만 허용. 기존 `is_admin()` 함수를 그대로 재사용하므로 신규 함수 작성이 필요 없다.
- **화면 접근(라우트 레벨)**: 기준정보 관리 5개 화면은 3.1절 규칙대로 `role in ('admin','superadmin')`을 서버에서 재검증하고, 아니면 기존 `/erp/forbidden`으로 이동시킨다(기본 관리 화면과 동일 패턴 재사용).
- 상품 관리 화면은 라우트 접근 자체는 기존 `user_menu_permissions` 로직을 그대로 따르되, 상품 데이터의 INSERT/UPDATE/DELETE는 필요 시 별도 정책으로 좁힐 수 있다(이번 문서 범위에서는 기존과 동일하게 개방 유지 — 별도 지시 없으면 상품 CRUD도 로그인 사용자 전체 허용으로 간주하고, 관리자만 허용해야 한다면 후속 확인 필요).

## 10. 더미 데이터 (엔티티당 10건)

> 실제 시드는 `supabase/seed.sql` 또는 마이그레이션으로 적용한다. 아래는 데이터 내용 정의이며, 데모 편의상 하위 데이터는 첫 번째 상위 항목(법인1, 브랜드1 등) 아래에 모두 배치했다.

**법인 (companies)**: `C1001~C1010`, 법인명 "법인 1"~"법인 10"

**브랜드 (brands, 전부 법인1 하위)**: `B1001~B1010`, "브랜드 1"~"브랜드 10"

**소브랜드 (small_brands, 전부 브랜드1 하위)**: `SB1001~SB1010`, "소브랜드 1"~"소브랜드 10"

**라인 (brand_lines, 전부 브랜드1 하위)**: `BL1001~BL1010`, "라인 1"~"라인 10"

**아이템타입 (item_types, 전부 소브랜드1 하위)**: `LC1001~LC1010`, "아이템타입 1"~"아이템타입 10"

**아이템 (items, 전부 아이템타입1 하위)**: `MC1001~MC1010`, "아이템 1"~"아이템 10"

**서브아이템 (sub_items, 전부 아이템1 하위)**: `SC1001~SC1010`, "서브아이템 1"~"서브아이템 10"

**컬러타입 (brand_color_types, 전부 브랜드1 하위)**: `BCT1001~BCT1010`, "컬러타입 1"~"컬러타입 10"

**컬러 (brand_colors, 전부 컬러타입1 하위)**: `BC1000001~BC1000010`, "컬러 1"~"컬러 10", `rgb_hex`는 서로 다른 임의 6자리 값(예: `FF5733`, `33A1FF`, ... 10개) 부여

**사이즈타입 (brand_gender_size_types, 전부 브랜드1 + 성별=남성 하위)**: `BGST1001~BGST1010`, "사이즈타입 1"~"사이즈타입 10"

**사이즈 (brand_gender_sizes, 전부 사이즈타입1 하위)**: `BGS1001~BGS1010`, "사이즈 1"~"사이즈 10"

**상품 (products, 전부 서브아이템1/라인1/컬러1 하위, 성별·사이즈만 다양화)**: `PM100000001~PM100000010`, "상품 1"~"상품 10", 성별은 남성/여성/혼용을 순환 배정, 사이즈는 사이즈1~10 중 하나씩 배정, 이미지/썸네일은 플레이스홀더 경로 사용

## 11. 비범위 (Out of Scope)

- 상품 정보 현황 / 상품 정보 일괄 수정 화면 상세 설계
- 재고·발주·매입/매출 등 상품 이후 단계 기능
- 코드 체계 다국어화, 엑셀 업로드/다운로드(대량 등록) — 후속 문서에서 별도 검토
- 컬러 RGB 값의 실제 색공간 검증(예: 인쇄/모니터 색상 프로파일 보정)

## 13. 성공 기준

- [ ] 법인/브랜드 구조/상품 분류/컬러/사이즈 5개 화면이 마스터-디테일 패턴으로 동작하고, 각 화면에서 계층 CRUD가 가능하다.
- [ ] `role = 'user'`인 계정은 `user_menu_permissions` 부여 여부와 무관하게 기준정보 관리 5개 화면에서 차단되고 `/erp/forbidden`으로 이동한다.
- [ ] `role in ('admin','superadmin')` 계정은 별도 권한 부여 없이 5개 화면에 접근 가능하다.
- [ ] 상품 등록 폼에서 서브아이템 선택에 따라 라인/컬러/사이즈 드롭다운이 동일 브랜드로 필터링된다.
- [ ] 상품 목록에서 썸네일(축소), 상세/등록 폼에서 원본 상품 이미지가 각각 올바르게 노출된다.
- [ ] 11개 마스터 엔티티 + 상품에 10건씩 더미 데이터가 시드되어 화면에서 즉시 확인 가능하다.
- [ ] `menus` 테이블이 4.3절 매핑대로 갱신되고, 기존 "브랜드 관리"/"소브랜드 관리" 등 URL을 통한 직접 접근 시에도 새 구조로 정상 리다이렉트/렌더링된다.
