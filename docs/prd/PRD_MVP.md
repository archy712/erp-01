# 사내 ERP 시스템 MVP PRD

> 문서 버전: v1.1 · 최초 작성일: 2026-08-15 · 최종 수정: 2026-08-15 (구현 단계/Phasing 반영)
> 기반 저장소: Next.js 16(App Router) + Supabase Auth 스타터킷 (`@supabase/ssr`, shadcn/ui `new-york`, Recharts, Lucide, next-themes, 자체 i18n)

---

## 1. 배경 및 목표

### 1.1 배경

현재 저장소는 Supabase 인증, shadcn/ui 컴포넌트 갤러리, 다크모드, 4개 언어 i18n이 세팅된 **스타터킷** 상태다. 이번 PRD는 이 스타터킷 위에 사내에서 실제로 쓸 ERP 애플리케이션의 **뼈대(메인 화면 레이아웃 → 인증 → 메뉴 → 권한 → 내비게이션)** 를 얹기 위한 MVP 요구사항을 정의한다.

이 프로젝트는 기존 스타터킷을 그대로 활용하는 것을 전제로 하며, 특히 `app/layout.tsx`의 **상단 Header(`AuthButton`, `ThemeSwitcher`, `LanguageSwitcher` 등 포함)와 하단 Footer는 그대로 유지**하고, 그 사이의 메인 콘텐츠 영역에 ERP 화면을 구성하는 방식으로 진행한다. 작업은 한 번에 전체를 구현하지 않고 **[2. 구현 단계 (Phasing)](#2-구현-단계-phasing)** 에 정의된 순서로 단계적으로 진행한다.

### 1.2 목표

- (Phase 1 최우선) 기존 Header/Footer를 유지한 채, 로그인 후 진입하는 **ERP 메인 화면**의 기본 레이아웃 뼈대(상단 Menubar + 좌측 트리메뉴 + 우측 콘텐츠 영역)를 먼저 구성한다.
- (Phase 2 이후) 이메일/비밀번호 및 구글 OAuth 인증을 완성하고, 데스크탑/태블릿/모바일에서 모두 사용 가능한 반응형을 확정한다.
- (Phase 2 이후) **메뉴(화면) 단위 권한 관리**를 구축하여, 관리자는 전체 메뉴에 접근하고 일반 사용자는 부여받은 메뉴만 조회할 수 있도록 한다.
- (Phase 2 이후) 사용자 관리 / 메뉴 관리 / 사용자 권한 관리는 실제 동작하는 기능으로 구현하고, 그 외 모든 업무 메뉴는 "제목만 표시되는 빈 화면"까지만 구현한다.

### 1.3 이번 MVP가 아닌 것

각 업무 메뉴(기준정보 관리, 상품 관리, 경영정보~게시판 등)의 실제 비즈니스 로직·데이터 CRUD는 이번 MVP의 목표가 아니다. MVP는 "그 화면으로 들어갈 수 있고, 권한이 없으면 보이지 않는다"까지만 보장한다. 또한 기존 스타터킷의 Header/Footer 자체를 새로 설계하는 것도 이번 MVP의 목표가 아니다 (그대로 유지). 자세한 내용은 [9. 비범위](#9-비범위-out-of-scope)를 참고.

## 2. 구현 단계 (Phasing)

이 프로젝트는 기존 Next.js 16 + Supabase Auth 스타터킷을 그대로 활용하며, 아래 순서로 단계적으로 구현한다. 이후 섹션(범위, 기능 요구사항, 화면별 상세 기능)의 각 항목은 이 Phase 구분을 기준으로 태그되어 있다.

### 2.1 Phase 0 — 전제 (변경 금지 대상, 작업 범위 아님)

- `app/layout.tsx`의 기존 **상단 Header**(`AuthButton`, `ThemeSwitcher`, `LanguageSwitcher` 등 포함)와 **하단 Footer**는 그대로 유지한다. 디자인/마크업/동작을 임의로 변경하지 않는다.
- 신규로 만드는 ERP 화면 요소(상단 Menubar, 좌측 트리메뉴, 우측 콘텐츠 영역 등)는 기존 Header와 Footer 사이의 메인 콘텐츠 영역 안에서만 구성한다.
- 스타터킷에 이미 구현되어 있는 기본 이메일/비밀번호 로그인 흐름(`app/auth/*`)은 Phase 1에서 별도 확장 없이 그대로 인증 게이트로 활용한다.

### 2.2 Phase 1 — ERP 메인 화면 우선 구현 (최우선)

- 로그인 후 진입하는 첫 화면, 즉 **ERP 메인 화면**(대시보드 성격의 랜딩/홈 화면)을 최우선으로 구성한다.
- 기존 Header/Footer 사이에 **상단 Menubar + 좌측 트리메뉴 + 우측 콘텐츠 영역**으로 이어지는 기본 레이아웃 뼈대를 구현한다 (반응형 포함, 모바일에서 트리는 Drawer로 전환).
- 이 단계에서는 메뉴 데이터가 비어 있거나 최소 수준(예: "마스터 관리" 정도의 하드코딩된 임시 트리)이어도 무방하다 — 목표는 데이터/권한 로직의 완성이 아니라 **레이아웃과 내비게이션 골격의 완성**이다.
- 메뉴/권한을 저장할 DB 테이블(`menus`, `user_menu_permissions`)이 아직 없어도 Phase 1은 진행 가능해야 한다.

### 2.3 Phase 2 이후 — 나머지 MVP 기능 순차 기획

Phase 1의 레이아웃 뼈대가 완성된 이후, 아래 기능들을 순차적으로 기획·구현한다 (세부 요구사항은 이 문서에 이미 정의된 내용을 그대로 참고):

- 이메일/비밀번호 인증 흐름 세부 완성(회원가입/비밀번호 재설정 등) 및 **구글 OAuth 인증** 추가
- **다크모드 토글**을 ERP 메인 화면 문맥에 맞게 최종 점검 (기존 `next-themes` 컴포넌트는 이미 Header에 있으므로 신규 개발이 아닌 통합 확인 수준)
- `menus`, `user_menu_permissions` 등 데이터 모델 구축 및 **메뉴 데이터 전체 등록** (마스터 관리 하위 3개 그룹 + 14개 대분류 Placeholder)
- **사용자 관리 / 메뉴 관리 / 사용자 권한 관리** 화면 구현 (관리자 전용, 실제 CRUD)
- 사용자 권한에 따른 **메뉴 접근 제어**(내비게이션 필터링 + 서버 재검증) 로직 적용
- 나머지 업무 메뉴(기준정보/상품/경영정보~게시판)를 플레이스홀더 화면과 실제로 연결

## 4. 사용자 및 권한 모델

> 이 섹션에서 정의하는 데이터/로직은 **Phase 2 이후**에 구현된다. Phase 1(ERP 메인 화면 뼈대)에는 실제 권한 체크 없이 로그인 여부만 게이트로 사용한다.

### 4.1 사용자 구분

| 구분                   | 설명                                                                                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **관리자 (admin)**     | 모든 메뉴에 무조건 접근 가능. 사용자 관리/메뉴 관리/사용자 권한 관리 화면은 관리자만 접근 가능. 초기 관리자 계정은 `archy712@gmail.com`으로 고정 지정 |
| **일반 사용자 (user)** | 관리자로부터 권한을 부여받은 메뉴만 조회 가능. 권한이 없는 메뉴는 트리/Menubar에서 보이지 않으며, URL 직접 접근도 차단됨                              |

### 4.2 권한 부여 단위

- 권한은 **화면(메뉴) 단위**로 부여한다. 역할(Role) 기반이 아니라 "사용자 ↔ 메뉴" 1:1 매핑 방식이다.
- 권한은 트리의 어느 레벨(대/중/소분류)에도 부여할 수 있다. 소분류에 권한이 있으면 그 상위(중분류, 대분류) 노드는 내비게이션에서 자동으로 함께 노출된다(경로 노출을 위한 것이며 상위 노드 자체에 대한 권한 부여는 아님).
- 관리자는 `user_menu_permissions` 데이터와 무관하게 전체 메뉴에 접근한다 (권한 체크 로직에서 `role = 'admin'`이면 항상 통과).

### 4.3 초기 관리자 지정 방식

- 최초 배포 시 시드 데이터/마이그레이션으로 `archy712@gmail.com` 계정에 `role = 'admin'`을 부여한다.
- 이후 관리자 권한의 추가/이전(다른 사용자를 관리자로 승격)은 사용자 관리 화면에서 관리자가 직접 수행한다.

## 5. 사용자 여정 (User Flow)

```
[비로그인 상태] (Phase 0 — 기존 스타터킷 인증 흐름 재사용)
  방문 → 로그인 페이지
           ├─ 이메일/비밀번호 입력 → 로그인
           ├─ "Google로 계속하기" 클릭 → Google OAuth 동의 화면 → 콜백 처리 → 로그인   ※ Phase 2에서 추가
           └─ "회원가입" 클릭 → 회원가입 페이지 → 이메일 인증 → 로그인 페이지로 복귀

[로그인 성공] (Phase 1 — ERP 메인 화면)
  → ERP 메인 화면(대시보드/홈) 진입 — 기존 Header/Footer는 그대로, 그 사이에 아래 구조 표시
       ├─ 상단 Menubar에서 대분류 클릭 → 좌측 트리에 중/소분류 표시
       │      └─ 트리에서 소분류(또는 리프 노드) 클릭 → 우측 콘텐츠 영역에 해당 화면 표시
       │             ├─ [일반 업무 메뉴] 제목만 표시된 빈 화면 (Out of scope 안내 배지 포함)     ※ Phase 2에서 데이터 연결
       │             └─ [마스터 관리 > 기본 관리] 사용자 관리 / 메뉴 관리 / 사용자 권한 관리      ※ Phase 2에서 실제 동작 구현
       ├─ (기존 Header의) 다크모드 토글 클릭 → 즉시 테마 전환
       └─ (기존 Header의) 사용자 메뉴 → 로그아웃 → 로그인 페이지로 리다이렉트

[권한 없는 메뉴 접근 시도] ※ Phase 2 이후 (권한 데이터가 있어야 성립)
  URL 직접 입력 등으로 접근 → 서버에서 권한 재검증 → 접근 불가 안내 화면 (홈으로 돌아가기 링크 제공)
```

## 6. 기능 요구사항

각 기능에는 ID를 부여하고, MVP에서 **실제 로직까지 구현**하는지 **메뉴/화면 뼈대만** 구현하는지, 그리고 **몇 번째 Phase**에서 다루는지를 함께 명시한다. (Phase 상세 정의는 [2. 구현 단계](#2-구현-단계-phasing) 참고)

### 6.1 인증 및 공통 UI

## 7. 화면/메뉴 구조 (와이어프레임)

### 7.1 레이아웃 구조

기존 Header/Footer(Phase 0, 변경 금지)는 그대로 유지하고, 그 사이의 메인 콘텐츠 영역에 아래 구조를 Phase 1에서 구성한다.

```
┌──────────────────────────────────────────────────────────────────┐
│ [기존 Header 그대로 유지] 로고 / AuthButton / ThemeSwitcher /       │  ← Phase 0, 변경 금지
│ LanguageSwitcher 등                                               │
├──────────────────────────────────────────────────────────────────┤
│  [마스터관리] [경영정보] [인사급여] [웹회계] ...  (대분류 Menubar)    │  ← Phase 1 신규
├───────────────┬──────────────────────────────────────────────────┤
│ 좌측 트리 영역  │                  우측 콘텐츠 영역                    │  ← Phase 1 신규
│               │                                                  │
│ ▾ 기본 관리    │        [선택한 소분류 화면 제목]                     │
│   · 사용자 관리 │                                                  │
│   · 메뉴 관리   │   (마스터관리>기본관리 하위 화면: Phase 2 실제 CRUD) │
│   · 권한 관리   │   (그 외 화면: 제목만 표시되는 빈 화면, Phase 1/2)   │
│ ▾ 기준정보 관리 │                                                  │
│   · 법인 관리   │                                                  │
│   · 브랜드 관리 │                                                  │
│   ...          │                                                  │
│ ▸ 상품 관리     │                                                  │
├───────────────┴──────────────────────────────────────────────────┤
│ [기존 Footer 그대로 유지]                                          │  ← Phase 0, 변경 금지
└──────────────────────────────────────────────────────────────────┘
```

- **기존 Header/Footer**: `app/layout.tsx`에 이미 구현되어 있으며 이번 작업에서 변경하지 않는다.
- **상단 Menubar (대분류)**: Phase 1에서 신규 구현. 클릭 시 좌측 트리가 해당 대분류의 중/소분류로 갱신됨.
- **좌측 트리 (중분류/소분류)**: Phase 1에서 신규 구현. 모바일 화면에서는 Sheet/Drawer로 전환되어 토글 버튼으로 열고 닫음.
- **우측 콘텐츠 영역**: Phase 1에서 뼈대(빈 화면 렌더링 메커니즘) 구현, Phase 2에서 마스터 관리 > 기본 관리 하위 3개 화면을 실제 기능 화면으로 완성.
- 로그인한 사용자에게 권한이 없는 메뉴는 Menubar/트리 어디에도 노출되지 않는다 (관리자는 항상 전체 노출) — 이 필터링 로직은 Phase 2 이후 적용.

### 7.2 전체 메뉴 트리

> 각 소분류 옆 괄호는 사용자가 제공한 참고용 필드 스펙이며, MVP에서는 메뉴 데이터(이름)만 등록하고 필드 기반 CRUD 로직은 구현하지 않는다 (마스터 관리 > 기본 관리 제외). 전체 메뉴 데이터 등록은 Phase 2 이후 진행하며, Phase 1에서는 레이아웃 검증용 최소 트리(예: "마스터 관리"만)를 사용해도 무방하다.

```
📁 마스터 관리
├── 📂 기본 관리                         ★ MVP 핵심 (Phase 2, 실제 구현)
│   ├── 사용자 관리
│   ├── 메뉴 관리
│   └── 사용자 권한 관리
├── 📂 기준정보 관리                      ☐ 메뉴 뼈대만 (Phase 2)
│   ├── 법인 관리 (법인코드, 법인명)
│   ├── 브랜드 관리 (브랜드코드, 브랜드명, 집계 브랜드, 사업부, 정렬순서, 등록가능여부, 사용여부, 비고)
│   ├── 소브랜드 관리
│   ├── 아이템/서브아이템 관리
│   ├── 상품 컬러 관리
│   └── 상품 사이즈 관리
└── 📂 상품 관리                          ☐ 메뉴 뼈대만 (Phase 2)
    ├── 상품 관리
    ├── 상품 정보 현황
    └── 상품 정보 일괄 수정

📁 경영정보    ☐ 대분류 Placeholder (중/소분류 향후 확정 예정, Phase 2)
📁 인사급여    ☐ 대분류 Placeholder (Phase 2)
📁 웹회계      ☐ 대분류 Placeholder (Phase 2)
📁 기획        ☐ 대분류 Placeholder (Phase 2)
📁 소싱        ☐ 대분류 Placeholder (Phase 2)
📁 물류        ☐ 대분류 Placeholder (Phase 2)
📁 협력사      ☐ 대분류 Placeholder (Phase 2)
📁 영업        ☐ 대분류 Placeholder (Phase 2)
📁 영업관리    ☐ 대분류 Placeholder (Phase 2)
📁 영업기획    ☐ 대분류 Placeholder (Phase 2)
📁 고객관리    ☐ 대분류 Placeholder (Phase 2)
📁 웹POS       ☐ 대분류 Placeholder (Phase 2)
📁 C&F         ☐ 대분류 Placeholder (Phase 2)
📁 게시판      ☐ 대분류 Placeholder (Phase 2)
```

- Placeholder 대분류 14개는 하위 중/소분류가 정해지지 않았으므로, 메뉴 관리 화면에서 **대분류 레벨 노드만 등록**해도 정상 동작해야 한다 (즉 메뉴 트리의 각 레벨은 하위 레벨 없이도 리프로 취급될 수 있어야 함). 클릭 시 F010 공용 빈 화면이 렌더링된다.
- 향후 하위 메뉴가 확정되면 메뉴 관리 화면에서 관리자가 직접 중/소분류를 추가하는 것으로 확장 가능해야 한다 (스키마 변경 불필요).

## 9. 비범위 (Out of Scope)

다음 항목은 이번 MVP에서 명시적으로 제외한다.

- **기존 Header/Footer의 재설계**: `app/layout.tsx`의 상단 Header, 하단 Footer는 그대로 유지하며 이번 프로젝트에서 변경하지 않는다.
- **업무 화면 실제 로직**: 마스터 관리 > 기준정보 관리(법인/브랜드/소브랜드/아이템/컬러/사이즈), 상품 관리(상품 관리/현황/일괄수정), 그리고 경영정보/인사급여/웹회계/기획/소싱/물류/협력사/영업/영업관리/영업기획/고객관리/웹POS/C&F/게시판의 **실제 데이터 CRUD, 조회/입력 폼, 비즈니스 로직**. 이번 MVP는 메뉴 등록과 빈 화면(F010) 노출까지만 다룬다.
- 사용자 프로필 상세 관리(아바타 업로드, 자기소개 등), 알림/설정 기능
- 역할(Role) 기반 권한 체계 (MVP는 "관리자/일반" 2단계 + 사용자별 메뉴 매핑만 지원, 그룹/부서 단위 권한은 제외)
- 메뉴 관리에서의 다국어 메뉴명 관리 (메뉴명은 우선 한국어 단일 값으로 관리)
- 감사 로그, 변경 이력 추적
- 대시보드 내 통계/차트 위젯의 실 데이터 연동 (Chart 컴포넌트 활용 자체는 In scope이나, 표시할 실제 업무 데이터는 Out of scope)

## 11. 기술 스택 (기존 스타터킷 재사용)

이번 MVP는 신규 라이브러리 도입 없이 기존 스타터킷 스택을 최대한 활용한다.

- **Next.js 16 (App Router)** + **React 19** + **TypeScript** — 기존 구조 그대로 (`app/`, `components/`, `lib/`는 루트, `src/` 미사용)
- **기존 Header/Footer (`app/layout.tsx`)** — Phase 0, 변경 없이 그대로 사용. `AuthButton`, `ThemeSwitcher`, `LanguageSwitcher`는 이미 구현되어 있으므로 신규 개발 대상이 아니다.
- **Supabase Auth (`@supabase/ssr`)** — 이메일/비밀번호 인증은 기존 `login-form.tsx` 패턴을 Phase 1에서 그대로 재사용하고, Phase 2에서 구글 OAuth(`supabase.auth.signInWithOAuth({ provider: "google" })`)를 추가한다. 인증 호출은 기존 관례대로 Server Action이 아닌 Client Component에서 직접 수행
- **shadcn/ui (`new-york`)** — Menubar(상단 대분류, Phase 1), Tree/Collapsible 조합(좌측 트리, Phase 1), Sheet(모바일 트리 Drawer, Phase 1), Table(사용자/메뉴 목록, Phase 2), Dialog/Form(등록·수정, Phase 2), Switch(사용여부·활성여부 토글, Phase 2), Badge(안내 배지, Phase 1)
- **Avatar 컴포넌트** — 기존 Header 사용자 메뉴에서 이미 사용 중, 사용자 관리 목록(Phase 2)에서 추가 활용
- **Recharts** — ERP 메인 화면 등에서 기존 차트 컴포넌트 재사용 가능 (실 데이터 연동은 Out of scope)
- **Lucide React 아이콘** — 메뉴 트리/Menubar 아이콘(Phase 1), 액션 버튼 아이콘(Phase 2)
- **next-themes** — 다크모드 토글, 기존 Header 컴포넌트를 그대로 사용 (Phase 2에서 통합 확인만 수행)
- **`proxy.ts` + `lib/supabase/proxy.ts`** — 인증 세션 갱신은 기존 로직 유지, 메뉴 접근 제어(F008)는 개별 페이지의 서버 컴포넌트에서 `getClaims()` + 권한 조회로 이중 방어 (기존 `app/protected/page.tsx` 패턴과 동일한 방식, Phase 2 이후)
